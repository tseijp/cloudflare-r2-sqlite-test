# 005 重い `sql` を止める仕組みが無く、その間ほかの命令が全て待たされる

状態: 未修正。判断待ち。

## 1. 発生条件

`sql` に、結果が出るまでに長く走る読み取りの文を渡す。再帰 CTE、大きな直積、全行の集計などである。`sql` は読み取りしか許さないが、走る時間には上限が無い。返す行は `ROWS` (100) で打ち切るが、1 行を作るまでの計算は打ち切らない。

## 2. 再現方法

command は全て repository の root (`projects/_cloudflare-r2-sqlite-test`) で実行する。

### 2.1. 数秒で終わる重い `sql`

```
node_modules/.bin/tsx .bench/run.mjs repro .bench/issues/005.json
```

操作列は `.bench/issues/005.json` にある。再帰 CTE で 1,000 万行を数える `sql` を送り、その直後 (終わるのを待たず) に `select 1` を送る。

出力 (2026-11-11 に実行したもの)。

```
-1 A open -> ok calls [["get",0,0,"…"]] store []
0 A page.add p -> ok store []
1 A sql select 1 -> ok [["1"],[1]] 0ms store []
2 A sql with recursive c(n) as (select 1 union all select n + 1 from c where n < 10000000) select count(*) from c -> ok [["count(*)"],[10000000]] 3735ms store []
2 A sql select 1 (直後に送った) -> ok [["1"],[1]] 3734ms
3 A sql select 1 -> ok [["1"],[1]] 0ms store []
```

| 見る行                     | 読み方                                                               |
| -------------------------- | -------------------------------------------------------------------- |
| `1 A sql select 1`         | 単独では 0 ms で返る                                                 |
| `2 A sql with recursive …` | 3,735 ms かかる                                                      |
| `2 … (直後に送った)`       | 同じ `select 1` が 3,734 ms 待たされる。重い `sql` が終わるまで進まない |

### 2.2. 終わらない `sql`

```
timeout 20 node_modules/.bin/tsx .bench/run.mjs repro .bench/issues/005b.json; echo exit $?
```

操作列は `.bench/issues/005b.json` にある。上限の無い再帰 CTE を数える `sql` を送る。

出力 (2026-11-11 に実行したもの)。

```
exit 124
```

20 秒たっても終わらず、`timeout` に kill される (exit 124)。出力は操作列が終わった後に書くので、何も出ない。process の event loop ごと止まる。

simulation の生成は終わらない文を作らないので、seed では当たらない。

## 3. 期待と観測

| 項目 | 内容                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------- |
| 期待 | contract に決まりは無い                                                                                 |
| 観測 | 1,000 万行の再帰 CTE で 3.7 秒、2,000 万行で 7.8 秒。その間、後から送った命令は待つ。timer も 1 度も進まない |

## 4. 仕組み

命令は 1 本の列に並んで順に走る。SQLite の wasm は、page の読みを待つとき以外は同期で走り続けるので、1 つの文が終わるまで event loop に戻らない。文を途中で止める仕組み (progress handler、interrupt) は付けていない。

## 5. 影響する範囲

`sql` を送れる全員である (画面の SQL 欄、LLM)。走っている間、その Durable Object は編集も save も窓の更新も進まない。終わらない文では、その Durable Object は止まったままになる。workerd の上で CPU 時間の上限に当たったときの動きは確かめていない。

## 6. 直す場合の案

| 案  | 内容                                                                                                                 | 行数の見込み              |
| --- | -------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 0   | 直さない                                                                                                             | 0                         |
| 1   | 読み取り専用の実行の間だけ progress handler を付け、SQLite の仮想機械の命令数が上限を超えたら文を中断して reject する | sqlite +3 行、定数 +1 行  |

案 1 は上限の値を決める必要がある。wa-sqlite 1.0.0 に `progress_handler(db, nProgressOps, handler, userData)` があることは source で確かめた。動かして確かめてはいない。

## 7. 判断がほしい点

`sql` に計算量の上限を付けるか。付けるなら値をいくつにするか。
