# 001 writer が 2 つのとき、merge と push の交差で保存済みの変更が消える

状態: 未修正。判断待ち。

## 1. 発生条件

同じ store を 2 つの instance (A と B) が開いていて、image が 2 chunk 以上である。

| 形  | 順序                                                        |
| --- | ----------------------------------------------------------- |
| 1   | B が push に成功する。その push を知らない A が merge する  |
| 2   | A が merge に成功する。その merge を知らない B が push する |

前提 (1 user 1 DO、同名の Durable Object は同時に 1 つ) が守られている間は起きない。

## 2. 再現方法

command は全て repository の root (`projects/_cloudflare-r2-sqlite-test`) で実行する。

### 2.1. 操作列の file で再現する

```
node_modules/.bin/tsx .bench/run.mjs repro .bench/issues/001.json
```

操作列は `.bench/issues/001.json` にある。`page.add`、`col.add`、2,000 文字 × 1,200 行の `import`、`save` で 2 chunk 以上の image を作り、形 1 (step 4) と形 2 (step 5) を続けて行う。

| 見る行                  | 読み方                                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------------------------- |
| `4 B save -> ok`        | B の push が成功し、store に delta 1 (`t2`) がある                                                        |
| `4 A save -> ok`        | B の delta を知らない A の merge が、image の tag `t1` を条件に通る。続く `delete` が B の delta 1 を消す |
| `4 崩れ … later save …` | 後から save した A が reject するはずが、解決している                                                     |
| `5 A save -> ok`        | A の merge が成功し、image の tag が `t4` になる                                                          |
| `5 B save -> ok`        | A の merge を知らない B の push が、番号 1 が空であることを条件に通る。delta 1 (`t5`) は鎖の外である      |
| `5 A open`              | 開き直すと、鎖に繋がらない delta 1 が消される。B が成功と受け取った save の内容は無い                     |

### 2.2. seed で再現する

```
node_modules/.bin/tsx .bench/run.mjs 548-548
```

約 35 秒かかる。stderr に `seed 548 medium mixed 119/119 steps, 3 failures, done` が出る。`.bench/out/` に新しい台帳ができ、`known` が `{"001": 3}`、`failures[]` に `known: "001"` の項目 (`compile/reject`、`単一書き/later save rejects`) が入る。

seed が作る操作列は検証 code (`test/`) の版で変わる。上の seed は 2026-11-11 の版のものである。同じ版で当たる他の seed は 438、568、637、638、678。

## 3. 期待と観測

| 項目 | 内容                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------- |
| 期待 | 後から `save` した側が reject し、store は先に成功した側の内容で開ける (`score.md` の単一書き)    |
| 観測 | 後から `save` した側も解決する。B が成功と受け取った `save` の内容は、次に開いたときに無い        |

## 4. 仕組み

1 回の save は条件付き put 1 回で、条件は書く object 1 つにしか掛からない。merge は image の tag、push は delta 番号が空であることを条件にする。database の状態は image と delta の複数 object にまたがるので、種類の違う save は互いを検出しない。

## 5. 影響する範囲

| 区分               | 内容                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 消えるもの         | 形 1 も形 2 も、B の保存済みの変更。B には成功と伝わっている                                                       |
| 壊れないもの       | store は常に開ける。鎖の外の delta は適用されない                                                                  |
| 起きない組み合わせ | image が 1 chunk の database (全ての save が image の put)、merge 同士、push 同士                                  |
| 後に続く症状       | B が生きて push を続けると、B の delta が鎖の外の番号に残り、A の push がその番号で `store conflict` になる。A の次の merge が番号 1 〜 8 を全て消すと解ける |

「後に続く症状」は、merge の `delete` を全番号にする前の版で観測した (seed 548、637 で、merge まで save が通らない状態が続いた)。今の版で merge のたびに解けることは、code の読みによる。

## 6. 直す場合の案

| 案  | 内容                                                                                                                                         | 検出できる範囲                                                            | R2 の請求                                                                 | 行数の見込み                   |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------ |
| 0   | 直さない。文書を実際の保証に合わせる (反映済み)                                                                                              | 同じ種類の save 同士                                                      | 変わらない                                                                | 0                              |
| 1   | put の前に相手側を 1 byte だけ get する。push の前は image の tag、merge の前は次の delta 番号の空き。今の「put が reject した後の確認」を置き換える | 時間の離れた交差の全て。確認と put の間に重なった save 同士は検出できない | 2 chunk 以上の save 1 回につき class B が 1 回増える (PUT の 8%)          | store で ±0 行                 |
| 2   | 全ての save を「次の番号が空なら書く」put にする。merge の image も次の番号に置く                                                            | 全て。put 1 回で順序が決まる                                              | open で最新の image を探す list 1 回 (class A)、または merge ごとに位置を書く put 1 回 | store、codec、page で +30 〜 50 行 |

## 7. 判断がほしい点

案 0、1、2 のどれにするか。決まるまでは案 0 のままにしてある。検証の「単一書き」の判定は、この形に当たると崩れ続け、「既知 001」として別に数えている。
