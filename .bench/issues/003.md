# 003 put が書いた後に reject すると、その Durable Object は開き直すまで save できない

状態: 未修正。判断待ち。

## 1. 発生条件

1. `save` の put が、object を書いた後に reject する (応答が届かない場合など)
2. 次の `save` が、その番号を 1 byte だけ get して確かめる。object が在る (delta) か、tag が変わっている (image) ので `store diverged` で reject する
3. それ以降の `save` は全て `store diverged` で reject する。`open` し直すと store の内容で続行できる

2 と 3 は contract どおりの動きである。アプリ (`src/server.tsx`) は `save` の reject を受けても `open` し直さない。利用者が画面から `open` を送れば復帰する (保存していない編集は捨てられる)。

## 2. 再現方法


## 3. 期待と観測

期待と観測は一致している (contract どおり)。問題は、この状態からアプリが自分で復帰しないことである。

| 時点                       | 状態                                                                            |
| -------------------------- | ------------------------------------------------------------------------------- |
| 1 の直後                   | store には 1 の save の内容が在る。製品はそれを知らない                         |
| 2 以降 (1 が delta の put) | 編集は memory と画面には反映されるが、store には 1 つも届かない                 |
| 2 以降 (1 が image の put) | memory に無い chunk を読む SQL が `disk I/O error` で失敗する。編集も通らない   |
| Durable Object の再起動後  | 1 の save の時点の内容で開く。1 より後の編集は無い                              |

## 4. 仕組み

put の成否が分からないとき、製品は「書けていない」ことだけを確かめて続行する。「書けていた」場合に、それが自分の書いた object かどうかを確かめる手段を持っていないので、別の writer が書いたものとして止まる。image が書けていた場合は、image の tag が覚えている tag と違うので、chunk の読みも止まる。

## 5. 影響する範囲

put が「書いた後に reject」した Durable Object 1 つである。store の内容は壊れない。失うのは、その put より後の、保存されなかった編集である。

## 6. 直す場合の案

| 案  | 内容                                                                                                           | 失うもの                                            | R2 の請求                         | 行数の見込み            |
| --- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | --------------------------------- | ----------------------- |
| 0   | 直さない                                                                                                       | 1 より後の全ての編集 (開き直すまで)                 | 変わらない                        | 0                       |
| 1   | アプリが `save` の reject を受けたら `open` し直す                                                             | 1 から reject までの編集。画面も store の内容に戻る | open の get が 1 回以上           | `server.tsx` +1 〜 2 行 |
| 2   | put の前に object の長さと hash を控える。確認で object が在ったら丸ごと読んで比べ、同じなら成功として続行する | 無し                                                | 確認の get が 1 byte でなく丸ごと | store +6 〜 8 行        |

## 7. 判断がほしい点

案 0、1、2 のどれにするか。案 1 と案 2 は両立する。
