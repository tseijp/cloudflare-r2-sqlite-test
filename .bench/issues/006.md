# 006 4 chunk (8 MiB) を超える database では、全走査の SQL のたびに chunk を R2 から読み直す

状態: 未修正。設計どおりの動きで、定数の判断待ち。

## 1. 発生条件

1. 圧縮前の database file が 4 chunk (8 MiB) を超える
2. 全ての leaf を読む SQL を実行する (集計、並べ替え、`DROP COLUMN`、LLM の `sql`)

製品が memory に持つ image の chunk は最大 `ROOM` = 4 個で、古い順に捨てる。chunk の数は圧縮前の file の大きさで決まり、圧縮後の image の大きさには依らない。

## 2. 再現方法

command は全て repository の root (`projects/_cloudflare-r2-sqlite-test`) で実行する。

node_modules/.bin/tsx .bench/run.mjs repro .bench/issues/006.json

### 2.3. 読み方

`calls` の `["get",0,…]` 1 つが R2 の GET 1 回 (class B) である。`calls` が無い行は store を呼んでいない。

| 操作列            | 全走査 1 回目     | 2 回目            | 3 回目            | 範囲読み 1 〜 3 回目 |
| ----------------- | ----------------- | ----------------- | ----------------- | -------------------- |
| 006 (6 chunk)     | 5 回 / 104,478 byte | 5 回 / 104,478 byte | 5 回 / 104,478 byte | 各 1 回 / 25,582 byte |
| 006b (4 chunk)    | 0 回              | 0 回              | 0 回              | 0 回                 |

6 chunk では、同じ全走査を繰り返すたびに 5 回の GET が出る。範囲読みの 1 回は、再現の道具が各 step の後に内容の照合のための全走査を挟み、その chunk が捨てられているためである。全走査を挟まなければ範囲読みは memory から返る (この点は実行して確かめていない)。

seed での再現は `node_modules/.bin/tsx /tmp/bench/mem837.mjs 837 1 4096` で行ったが、この driver は repository の外にある。

## 3. 期待と観測

期待と観測は一致している (`cost.md` 3 節「並べ替えや集計は全 leaf を読むので、image の chunk 数だけ GET する」)。繰り返しのたびに読み直すことは書いていなかったので、同じ節に足した。

## 4. 仕組み

chunk の cache は LRU で 4 個である。6 chunk を順に読む走査は、読み終えた時点で先頭側の chunk を捨てているので、次の走査でまた読む。走査 1 回の GET は (chunk 数 − 1) 回になる。

## 5. 影響する範囲

| 区分         | 内容                                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| 請求         | 8 MiB を超える database の全走査 1 回につき、class B が (chunk 数 − 1) 回。上限の 32 MiB では 15 回         |
| 時間         | 006 の全走査は 139 〜 152 ms、006b は 44 〜 48 ms (同じ機械、simulation の store)                           |
| 起きない操作 | cell の確定、行の追加、窓の読み (`_id` の範囲)。触る chunk が少なく、cache に残る                           |
| memory       | chunk の cache は最大 8 MiB。読み直すたびに 2 MiB の buffer を作って捨てる                                 |

## 6. 直す場合の案

| 案  | 内容                                                                              | GET                                    | memory                                   | 行数の見込み |
| --- | --------------------------------------------------------------------------------- | -------------------------------------- | ---------------------------------------- | ------------ |
| 0   | 直さない (`ROOM` = 4)                                                             | 全走査のたびに (chunk 数 − 1) 回       | chunk の cache は最大 8 MiB              | 0            |
| 1   | `ROOM` を 16 (= `LIMIT` ÷ `CHUNK`) にする                                         | chunk ごとに 1 回だけ。読み直しは無い  | chunk の cache は最大 32 MiB             | 定数 1 つ    |
| 2   | `ROOM` を 8 にする                                                                | 16 MiB までの database で読み直しが無い | chunk の cache は最大 16 MiB             | 定数 1 つ    |

Durable Object の稼働秒の単価は 128 MB ぶんで固定で、使った memory の量に依らない (`cost.md` 1 節)。memory の上限は 128 MB で、案 1 のとき、chunk の cache 32 MiB と保存前の page (上限まで一度に取り込むと最大 32 MiB) と SQLite の wasm の heap と yjs の doc が同時に載る。合計は測っていない。

## 7. 判断がほしい点
