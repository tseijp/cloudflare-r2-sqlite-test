# 004 rollback された書き込みの後の `save` が、内容の同じ page を put する

状態: 未修正。判断待ち。

## 1. 発生条件

1. 書き込みの transaction が、page を file (page 層) に書いた後で rollback される
2. その後に `save` を呼ぶ

観測した形は、上限 (8,192 page) を超える `import` が `database or disk is full` で reject する場合である。SQLite は、cache から溢れた page を commit の前に file へ書くので、大きな transaction で起きる。

## 2. 再現方法

command は全て repository の root (`projects/_cloudflare-r2-sqlite-test`) で実行する。

### 2.1. 操作列の file で再現する

```
node_modules/.bin/tsx .bench/run.mjs repro .bench/issues/004.json
```

操作列は `.bench/issues/004.json` にある。空の page を保存し、4,000 文字 × 8,500 行 (上限を超える量) を `import` し、`save` を 2 回送る。

出力 (2026-11-11 に実行したもの)。

```
-1 A open -> ok calls [["get",0,0,"…"]] store []
0 A page.add p -> ok store []
1 A col.add p -> ok store []
2 A save -> ok calls [["put",0,"…"]] store [[0,"t1"]]
3 A import p -> reject: database or disk is full store [[0,"t1"]]
4 A sql select count(*) from "p" -> ok [["count(*)"],[0]] 1ms store [[0,"t1"]]
5 A save -> ok calls [["put",0,"…","t1"]] store [[0,"t2"]]
5 崩れ 回数/clean (既知 004) 期待 "no store call without a change" 観測 {"dirty":2,"sig":[["put",0,442,"t1"]]}
6 A save -> ok store [[0,"t2"]]
```

| 見る行                 | 読み方                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------- |
| `3 A import -> reject` | 上限を超えて reject し、transaction は rollback される                             |
| `4 A sql`              | 行数は 0 のままで、内容は 2 の save の時点と同じ                                   |
| `5 A save -> ok`       | 変化が無いのに `put` を 1 回呼ぶ。`dirty` が 2 で、442 byte の同じ image を書き直す |
| `6 A save -> ok`       | 2 回目は store を呼ばない                                                          |

### 2.2. seed で再現する

```
node_modules/.bin/tsx .bench/run.mjs 429-429
```

約 87 秒かかる。stderr に `seed 429 large every 211/211 steps, 1 failures, done` が出る。新しい台帳の `known` が `{"004": 1}`、`failures[0]` が `回数/clean` (`known: "004"`、観測 `{"dirty":6,"sig":[["put",1,12170,""]]}`) になる。こちらは 2 chunk 以上の database で、6 page の delta (12,170 byte) を put している。

seed が作る操作列は検証 code (`test/`) の版で変わる。上の seed は 2026-11-11 の版のものである。同じ版で当たる他の seed は 589。

## 3. 期待と観測

| 項目 | 内容                                                                            |
| ---- | ------------------------------------------------------------------------------- |
| 期待 | 変化が無ければ store を呼ばない (`SKILL.md` の 3.5)                             |
| 観測 | rollback の後の最初の `save` が `put` を 1 回呼ぶ。書く内容は store にあるものと同じ |

## 4. 仕組み

page 層は、SQLite が書いた page の番号を `dirty` に入れる。rollback のとき SQLite は元の内容を同じ page に書き戻すが、page 層はそれを新しい書き込みとして受け取る。内容が元に戻ったことを知らないので、`dirty` に残る。

## 5. 影響する範囲

rollback 1 回につき、次の `save` で PUT (class A) が 1 回余分に出る。内容は壊れない。小さい transaction の失敗 (同名の `page.add` など) は、commit の前に page を file へ書かないので起きない。

## 6. 直す場合の案

| 案  | 内容                                                                                                                                             | 行数の見込み               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| 0   | 直さない                                                                                                                                         | 0                          |
| 1   | page 層が「この命令で初めて dirty になった page」を覚える。命令が失敗し、page 1 の change counter が命令の前と同じなら、その page を dirty から外す | page +5 行、executer +3 行 |

## 7. 判断がほしい点

rollback 1 回につき PUT 1 回の余分を許すか、8 行ほど足して無くすか。
